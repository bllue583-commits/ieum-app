## 0. 한 줄 결론

**v3.6으로 배터리는 잡았지만 그 값으로 "당일 정리"를 잃었다.** 통화에서 결과까지 중앙값 38시간, 아침 카톡 보고에는 어제 업무 통화의 약 60%만 들어가고(11/10: 14건/녹음 있는 업무 통화 23건, 추정) 빠진 통화는 말없이 빠진다. 그래서 v4.0까지는 **새 기능을 만들지 않는다.** 네 버전 모두 "이미 약속한 것을 지키게 하는" 버전이다.

## 3. v3.8 「넘치지 않는 저장소, 잠긴 배포」

### 3.1 저장소 (r18-1) — 기한 있는 일: 11/17까지 배포

구조(감사): 봉인 DB는 메모리 SQLite를 **쓰기 트랜잭션마다 모든 테이블·모든 행을 JSON 하나로 만들어 AES-GCM으로 파일 전체를 다시 쓴다**(`ProtectedDatabase.java:151, 284-319, 265-273` — 쓰기 한 번에 파일 I/O 세 번). 한도는 평문 16MiB·한 행 1MiB·10만 행이고 `dbPercent`는 파일 길이 비율과 행 수 비율 중 큰 값이다. 100%에 닿으면 `snapshot()`이 예외를 던져 **그 뒤 모든 쓰기가 실패**하고, 호출부의 `runCatching`(앱 전체 470곳)이 이를 삼켜 조용히 멈춘다(추정). 2분 조각마다 `savePart`가 전체를 다시 봉인하므로 DB가 클수록 자막도 느려진다.

| # | 내용 | 위험과 대책 |
| --- | --- | --- |
| S1 | **원문 분리.** `call_records.transcript`·`segments_json`과 문자 본문을 기록별 AES-GCM 파일(`noBackup/transcripts-v1/<id>.sealed`, AtomicFile)로. DB에는 sha와 길이만 | 순서 "파일 쓰기 → 다시 읽어 검증 → 같은 트랜잭션에서 칼럼 비움", 읽기는 파일 없으면 옛 칼럼(대체 길)을 1개 버전 동안 유지, 단계마다 반복해도 안전 |
| S2 | **조각 저장을 DB 밖으로.** `call_transcription_parts`를 녹음별 파일로 — 2분마다 전체 재봉인이 사라짐 | 끝낸 조각 무효화 금지(이어 하기), 옮기는 중 실행 금지(실행 작업 취소 뒤 이전) |
| S3 | **지울 수 없는 원장 줄이기.** `request_bindings.request_json`·`discovery_intake_requests.commit_payload`·`local_intakes.metadata_json`은 새 행부터 본문 대신 sha만. 기존 행은 그대로(BEFORE DELETE 트리거) | v3.7 `dbTables`로 실제 비중을 본 뒤 범위를 정함. 30% 넘는 테이블이 있으면 별도 `.sealed` 샤드(C안, `ContactCards` 선례) |
| S4 | **100%를 조용히 넘지 않기.** 쓰기 실패 사유 `TEXT_STORE_CAPACITY_REQUIRES_REVIEW`를 삼키지 말고 계수 → 신호등 "저장 공간이 다 찼어요"(주황)·워치독 | — |

지킬 것(데이터를 잃지 않으려면): `.sealed` 파일 이름·경로를 바꾸지 않는다(Keystore 별칭·AAD가 경로에서 나옴). `.bak`/`.new`는 복구 로직에 맡긴다. `format=1` 유지. 이전 전 `.sealed` 복사본을 7일 보관. 이전 전후 테이블별 행 수를 하트비트 `dbMigrate{before, after, moved, failed}`로. device-test에 8MB 합성 DB 이전 시나리오. **한도 상향(A안)은 하지 않는다** — 복원 시간·쓰기 비용이 그대로고 옛 빌드가 못 연다.

확인 기준: `dbPercent` < 30, `dbOpenMs` < 600, 하루 증가 < 0.3%p, `dbMigrate.failed` 0, 통화 상세에서 자막이 전과 같이 보임(화면 시험), 조각 저장 ms가 DB 크기와 무관.

### 3.2 배포 잠금 (r18-2, 사용자 할 일 포함 — 순서를 바꾸면 설치가 깨진다)

지금 상태(감사, 전부 열림): 우편함 토큰이 APK에 평문(`build.gradle.kts:22-24`), 서명 시드가 비면 서명 키가 그 토큰에서 파생(`derive_signing_key.py:29-31`), 폰은 APK sha256만 보고 인증서는 비교하지 않음(`CallUpdate.kt:309, 462`), 배포본이 `assembleDebug`(디버깅 가능, `SYNTHETIC_TOOLS=true`), 번호 해시는 소금 없는 SHA-256이고 개인 번호 해시가 공개 저장소 코드에 있음(`LocalPrivacy.kt:14`).

1. (사용자) GitHub 비밀 `IEUM_SIGNING_SEED`에 **지금** 우편함 토큰 값을 복사 — 서명 키가 토큰에서 독립.
2. (앱) 받은 APK의 서명 인증서를 설치 전에 자기 인증서와 비교, 다르면 설치하지 않고 `update.error=CERT`. 무인 설치는 통화 중·자막 실행 중에는 미룸.
3. (배포) `assembleRelease`(debuggable 끔, 합성 도구 끔). 같은 키라 덮어 설치됨 — update-smoke 필수.
4. (사용자) 토큰을 ieum-inbox contents 권한만 가진 세분화 토큰으로 교체. 1번이 끝난 뒤에만.
5. (앱) 번호 해시에 기기 비밀 소금(봉인 설정의 무작위 32바이트), 개인 번호 목록은 코드 상수에서 설정으로. `status/calllog.txt`의 개인 판정 줄은 이름·번호 가림.
6. (사용자) 저장소 비공개 복귀 + Actions 분량 조정(device-test는 수동·통합 브랜치만, inbox-e2e 하루 2회).

한계를 사실대로: 서버가 없는 구조라 **토큰을 APK에서 없앨 수는 없다.** 할 수 있는 것은 범위를 우편함 하나로 줄이고(4), 토큰을 얻어도 서명·설치로 이어지지 않게 끊는 것(1·2)이다.

### 3.3 코드 정리 (r18-3, 동작 변화 없음)

`CallRecordStore.kt`(1,619줄·함수 158개, 책임 12가지)를 스키마·장부·새벽 정리·처음 정리와 대조·카드·진단으로 **옮기기만** 한다(시험 그대로 통과가 조건). 저장 경로의 `runCatching`은 실패를 `swallowed{자리: 건수}`로 센다. 회차 표식 주석 삭제.

## 4. v3.9 「빠르고 정확한 자막」

### 4.1 왜 엔진인가

녹음 1분에 CPU 3.5분, 시간의 77%가 인코더다. large-v3-turbo는 **디코더만** 32층에서 4층으로 줄인 모델이라 GPU에서는 빠르지만, 인코더가 지배하는 폰 CPU에서는 이득이 작다(Distil-Whisper가 보인 속도 향상도 디코더 축소에서 나온다 — Gandhi et al., 2023). 이 속도에서는 배터리 예산 20분이 녹음 6분이라 "저녁에 오늘 통화"는 구조적으로 불가능하다. 반대로 실시간의 절반(1분에 30초) 이하 엔진이면 같은 예산으로 40분 — 하루치 대부분이 당일에 끝난다. 그리고 자막 정확도는 v3.3부터 "획기적 개선"이 목표였지만 **실녹음으로 한 번도 재지 못했다**(`golden: null`, 사용자 받아쓰기 0건).

## 6. 일하는 방식에서 바꿀 것 (평가서 4절의 결론)

1. **실측 게이트를 지킨다.** 배포 뒤 확인 기준 판정표(통과/실패/미확인)를 HANDOFF 4절에 채우기 전에는 다음 버전 코드를 배포하지 않는다. 11/6 "48시간을 기다리지 않음"으로 v3.2~v3.5를 하루에 쌓은 것이 v3.5 재큐 → 배터리 60% 사고의 배경이다. 최소 평일 하루.
2. **대기열을 늘리는 변경은 전력·처리량 계산을 설계에 적는다**(들어오는 분, 처리하는 분, 예산).
3. **사용자 손이 필요한 게이트를 줄인다.** 지금까지 사용자 할 일(실녹음 골든, S26 체크리스트, 서명 시드, 배터리 스크린샷)은 하나도 이행되지 않았다. 설계가 사람 손에 걸리지 않게(은 골든, 폰이 계산하는 포함률) 하고, 꼭 필요한 것은 10절에 날짜와 함께 3개 이하로.
4. **새 기능 동결.** v4.0까지 사용자에게 새로 보이는 것은 "빠진 건수를 말하는 보고"와 [틀렸어요]뿐.
5. 작업 브랜치에서 ci를 통과한 뒤 lean-calls에 합친다(1047 실수 재발 방지 — lean-calls 직접 push는 문서만).
