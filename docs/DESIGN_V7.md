## 4. v3.8 「넘치지 않는 저장소, 잠긴 배포」 + 엔진 측정대

### 4.1 저장소 (r18-1, 빌드 A) — 기한 있는 일: 11/17까지 배포

v3.8은 **두 번에 나눠 배포한다**: 빌드 A 저장소 → 평일 하루 판정 → 빌드 B 배포 잠금(4.2). 데이터 이전과 서명·빌드 유형 전환을 한 배포에 쌓지 않는다(6절 1번). 기한의 근거인 "11/25쯤 100%"는 직선으로 이은 값이고, 처음 정리로 한꺼번에 분석된 통화들의 14일 비움이 곧 시작되면 느려질 수 있다(추정) — v3.7의 `dbTables`와 응급 처치 결과를 보고 기한을 다시 잡는다.

구조(감사): 봉인 DB는 메모리 SQLite를 **쓰기 트랜잭션마다 모든 테이블·모든 행을 JSON 하나로 만들어 AES-GCM으로 파일 전체를 다시 쓴다**(`ProtectedDatabase.java:151, 284-319, 265-273` — 쓰기 한 번에 파일 I/O 세 번). 한도는 평문 16MiB·한 행 1MiB·10만 행이고 `dbPercent`는 파일 길이 비율과 행 수 비율 중 큰 값이다. 100%에 닿으면 `snapshot()`이 예외를 던져 **그 뒤 모든 쓰기가 실패**하고, 호출부의 `runCatching`(앱 전체 470곳)이 이를 삼켜 조용히 멈춘다(추정). 2분 조각마다 `savePart`가 전체를 다시 봉인하므로 DB가 클수록 자막도 느려진다.

지킬 것(데이터를 잃지 않으려면): `.sealed` 파일 이름·경로를 바꾸지 않는다(Keystore 별칭·AAD가 경로에서 나옴). `.bak`/`.new`는 복구 로직에 맡긴다. `format=1` 유지. 이전 전 `.sealed` 복사본을 7일 보관(사본에는 그 사이 지운 개인 통화 내용이 남으므로 7일 뒤 반드시 삭제; AAD가 경로라 사본은 **원래 경로로 되돌려야만** 열린다 — 복구 절차에 적는다). 이전 전후 테이블별 행 수를 하트비트 `dbMigrate{before, after, moved, failed}`로. device-test에 8MB 합성 DB 이전 시나리오. **한도 상향(A안)은 하지 않는다** — 복원 시간·쓰기 비용이 그대로고 옛 빌드가 못 연다.

확인 기준: `dbPercent` < 30, `dbOpenMs` < 600, 하루 증가 < 0.3%p, `dbMigrate.failed` 0, 통화 상세에서 자막이 전과 같이 보임(화면 시험), 조각 저장 ms가 DB 크기와 무관.

### 4.2 배포 잠금 (r18-2, 빌드 B, 사용자 할 일 포함 — 순서를 바꾸면 설치가 깨지거나 폰이 고립된다)

지금 상태(감사, 전부 열림): 우편함 토큰이 APK에 평문(`build.gradle.kts:22-24`), 서명 시드가 비면 서명 키가 그 토큰에서 파생(`derive_signing_key.py:29-31`), 폰은 APK sha256만 보고 인증서는 비교하지 않음(`CallUpdate.kt:309, 462`), 배포본이 `assembleDebug`(디버깅 가능, `SYNTHETIC_TOOLS=true`), 번호 해시는 소금 없는 SHA-256이고 개인 번호 해시가 공개 저장소 코드에 있음(`LocalPrivacy.kt:14`).

1. (사용자) GitHub 비밀 `IEUM_SIGNING_SEED`에 **지금** 우편함 토큰 값을 복사 — 서명 키가 토큰에서 독립.
2. (앱) 받은 APK의 서명 인증서를 설치 전에 자기 인증서와 비교(키 계보로 이어진 인증서는 허용), 다르면 설치하지 않고 `update.error=CERT`. 무인 설치는 통화 중·자막 실행 중에는 미루되 최대 24시간.
3. (배포) `assembleRelease`(debuggable 끔, 합성 도구 끔). **release 빌드 유형에 지금과 같은 keystore 서명 설정을 먼저 넣는다** — 지금은 debug에만 있어(`build.gradle.kts:11-12, 41-45`) 그대로면 서명 없는 APK가 나온다. `lintVitalRelease`가 빌드를 막는지 확인. update-smoke는 "debug 1049 위에 release 덮어 설치" 경로로 필수.
4. (사용자 + 배포) 토큰 회전: **새 토큰을 `IEUM_INBOX_TOKEN`에 넣고 배포 → 하트비트 versionCode가 그 빌드인지 확인 → 그 뒤에만 옛 토큰 폐기.** 토큰이 APK 안에 있으므로 옛 토큰을 먼저 없애면 폰이 `version.json`도 APK도 못 받아 업데이트 길이 끊긴다(검토 치명 C1). 1번이 끝난 뒤에만.
5. (앱) 번호 해시에 기기 비밀 소금(봉인 설정의 무작위 32바이트) — 기존 해시가 모두 달라지므로 **폰 안에서 한 번 다시 해시하는 이전**을 같이. 개인 번호 목록은 코드 상수에서 설정으로. `status/calllog.txt`의 개인 판정 줄은 이름·번호 가림.
6. (사용자) 저장소 비공개 복귀 + Actions 분량 조정(device-test는 수동·통합 브랜치만, inbox-e2e 하루 2회).

한계를 사실대로: 서버가 없는 구조라 **토큰을 APK에서 없앨 수는 없다.** 할 수 있는 것은 범위를 우편함 하나로 유지하고 주기적으로 바꾸며(4), 토큰을 얻어도 서명·설치로 이어지지 않게 끊는 것(1·2)이다.

채점용 표시: release-apk가 `app/version.json`에 `buildType`·`seedIndependent`를 쓰고, 폰이 하트비트 `security`에 `certCheck`·`saltedHash`를 쓴다. 비밀 스캔(gitleaks, 11/10 전체 이력 0건)은 ci 단계로 넣고 결과 건수를 우편함 `status/secrets-scan.json`에.

### 5.3 두 번 돌리기 설계 (규칙 2일 때)

| 단계 | 언제 | 무엇 | 화면 |
| --- | --- | --- | --- |
| 초벌 | 통화 끝난 직후, 배터리로(하루 상한 10분 — 시뮬레이션 상위 10% 날 4~5분) | 빠른 엔진으로 전체 자막 → 바로 업로드 → 다음 매시간 분석 | 통화 목록·저녁 알림·**아침 보고**에 요약. 숫자가 든 체크할 일에는 "확인 중" 배지 |
| 확정 | 충전 중(지금의 대기열·전력 정책·조각 이어 하기 그대로) | **업무 통화 전체**를 Whisper로. 초벌과 확정 자막을 글자 단위로 맞춰 숫자·이름이 다른 곳을 찾는다 | 같으면 배지 지움. 다르면 수정 요청 |
| 수정 | 숫자·이름이 달라진 통화만 | 요청에 두 자막의 차이를 실어 보내고, 결과 형식에 `revise{taskId, field, old, new, quote}`. 폰은 기록의 `analysis_rev`를 올려 그 칸만 고친다 | 고친 체크할 일에 "확인 필요". **끝낸 항목·사용자가 고친 항목은 바꾸지 않고** "숫자가 달랐어요" 알림만 |

- **지금 코드에는 수정 경로가 없다:** `applyInTransaction`은 이미 분석된 기록이면 그냥 돌아가고(`CallRecordStore.kt:784`), 중복 판정이 제목 기준이라 숫자가 바뀐 제목은 새 체크할 일로 또 생긴다(:821-823). hourly.md에도 수정 형식이 없다. r19에서 형식·적용·시험을 같이 만든다(지시문 v10).
- "숫자가 나온 구간만 다시"는 하지 않는다. Whisper는 구간이 짧아도 30초 창을 통째로 인코딩해 오히려 비싸고, 묵음을 지운 조각의 시각은 원래 시각으로 정확히 되돌릴 수 없으며(`PipelineAudioMath.kt:397`), 초벌에서 숫자가 빠지면 후보로 잡히지도 않는다.
- 채점 항목 1의 `inReport`는 초벌이 들어간 통화를 포함한다(아침 보고가 확정본을 기다리면 다시 충전에 묶인다). 보고에는 "확인 중인 숫자 n개"를 적는다.
- "충전 중에만" 스위치는 **확정 단계에만** 적용한다(초벌은 하루 몇 분). 스위치를 켠 채로도 저녁 약속이 성립한다.
- 확정이 밀려도(바쁜 날, 늦게 꽂은 밤) 초벌이 이미 보고에 들어가 있으므로 완전성은 지켜지고, "확인 중" 배지가 하루 더 남을 뿐이다.
- 아내가 최근 앱 목록에서 앱을 밀어 끄는 습관: 초벌 작업은 WorkManager가 다시 깨우고(통화 끝 방송 → 작업 예약), 몇 초짜리라 다시 시작해도 손해가 작다. 하트비트 `draft{killed, retried}`로 센다.
- 묵음 환각 대책: Silero VAD로 말소리 구간만 넣고, 1초 미만 조각의 한두 글자 출력은 버린다. "자막 인용이 있어야 체크할 일이 남는다" 규칙은 그대로.
- 라이선스: SenseVoice 가중치는 FunASR 모델 라이선스(사용 허용, 출처 표기 의무) → 설정 › 정보와 `THIRD_PARTY_NOTICES.md`에 표기. sherpa-onnx는 Apache-2.0. release 빌드에서 축소(minify)를 켜게 되면 sherpa JNI 클래스에 keep 규칙.

확인 기준(평일 5일): 항목 1 포함률 ≥ 95% 매일, 항목 2 그날 지연 p50 ≤ 180분·p90 ≤ 1,200분, 배터리 실행 ≤ 24분/일, 통화 1건당 mAh를 HANDOFF에 기록(규칙 2면 초벌과 확정의 숫자 불일치율도).

## 9. 일하는 방식

1. **채점이 먼저.** 버전마다 배포 뒤 `score.py`를 돌려 HANDOFF 4절에 점수와 판정표를 적는다. 판정 전에는 다음 버전을 배포하지 않는다(최소 평일 하루).
2. **코드를 쓰기 전에 시뮬레이션.** 대기열·예약 작업·전력에 닿는 변경은 `queue_sim.py`에 정책을 추가해 숫자를 설계에 적는다(v3.5 재큐는 이 단계가 있었다면 배포되지 않았다).
3. **사람 손은 "고르기"만.** 사용자 할 일은 12절의 것뿐이고 각각 20~40분 안.
4. **검토는 닫아야 끝.** 치명·높음은 같은 버전이나 바로 다음 배포에서 닫는다.
5. **새 기능 동결.** v4.0까지 사용자에게 새로 보이는 것은 빠진 건수를 말하는 보고, "확인 중" 배지, [틀렸어요]뿐.
6. 작업 브랜치에서 ci 통과 뒤 lean-calls에 합친다. lean-calls 직접 push는 문서·도구(`[skip ci]`)만 — `tools/**` 변경도 배포를 일으키므로 주의.

| r17-1 (T3) | 배터리 대기열의 녹음 길이를 `call_log`에서, 짝짓기 창(녹음 시각 2분 전~1분 뒤) 안에서 녹음 시각에 **가장 가까운** 받은·건 통화의 길이로 | 창 안 받은·건 통화 길이의 **`MAX(duration_ms)`**, 상관 부질의는 기본 테이블(`r0`, `l0`)에 걸음(`CallTranscriptionStore.kt` `lengthSql`) | 호스트 시험(Robolectric)의 SQLite가 상관 부질의 안의 `ORDER BY abs(cl.start_ms-$at)`와 파생 테이블 열 참조를 풀지 못함. 가장 긴 것을 고르면 애매한 짝은 길게 잡혀 충전 쪽으로 감(보수적) |

| r17-3 | `use{opens, homeSec, taskDone, notifTap, cardExpand, kakaoOpen}` 앱이 직접 셈 | `cardExpand`는 따로 세지 않고 카드 자체 집계(`CardStats`의 오늘 `expanded`)를 읽어 씀(`UseStats.cardExpandToday`). 사용 숫자는 메모리에 모아 화면이 뒤로 갈 때와 하트비트 때만 봉인 설정에 씀 | 묶음 지시문이 기존 `expanded`를 그대로 써도 된다고 함(같은 사건을 두 곳에서 세면 어긋남). 누를 때마다 봉인 DB 전체를 다시 쓰지 않음 |
| r17-3 | 자막 실행마다 **스레드** CPU 시간(`/proc/self/task/*/stat`) | **프로세스 전체** CPU 시간(`/proc/self/stat`의 utime+stime) 차이를 `power.today.cpuMs`·`cpuRuns`에, 배터리 실행의 `CHARGE_COUNTER` 차이를 `batteryUah`에 | 묶음 지시문(r17-3 8번 "가능한 범위")이 프로세스 값으로 정함. 실행 동안 같은 프로세스의 다른 작업(카드·결과 받기)의 CPU도 섞이므로 통화 1건당 CPU는 상한으로 읽는다 |
| r17-3 | `dbTables`: 테이블별 행 수와 글자 길이 합 상위 8개, 하루 증가분 | `dbTables{day, atMs, totalRows, totalChars, top[{name, rows, chars, dChars}]}`: 증가분은 표마다 **`dChars`**(지난 집계 뒤 글자 수 변화, 처음은 null). 전체 표 수치는 설정에만 두고 하트비트에는 상위 8개만 | 하루 증가분을 표 단위로 보아야 v3.8에서 어느 표를 줄일지 정함 |
