## 할 일

### r22-1 연결 안 된 녹음도 개인 검사를 지나가지 못하게 (필수)
- **먼저 코드로 사실을 확인한다**: 녹음 → 통화 기록 연결(`callLogMatch`, `RecordingGap`, `FirstPass`, `CallRecordStore`의 연결 함수들)이 실패했을 때 그 녹음의 기록이 어떤 상태로 업로드 대기열에 들어가는지, `counterpartKey`·이름 칸이 어떻게 채워지는지, `length` 실패의 판정 기준(녹음 길이와 통화 기록 길이의 허용 차이)이 무엇인지, 연결이 나중에(통화 기록이 늦게 읽힌 뒤) 다시 시도되는지.
- **고칠 것(설계는 코드 확인 뒤 정하되 아래 원칙을 지킨다):**
  1. **연결되지 않은 녹음은, 개인이 아니라고 볼 근거가 생길 때까지 올리지 않는다.** 근거 = (가) 통화 기록과 연결되어 번호가 개인 목록(`personal_numbers`)에 없음, 또는 (나) 녹음 파일 이름의 상대 이름·번호(`RecordingNames.callerAlias`, `PrivacyRules.phoneTokens`)가 개인 번호의 이름·번호와 겹치지 않음이 확인됨. 개인 번호의 이름은 폰 안의 통화 기록(`call_log`의 이름 칸)이나 이미 저장된 사람 정보에서 얻는다(새 권한을 요청하지 말 것 — 지금 가진 권한 안에서).
  2. 파일 이름의 상대가 개인 번호의 이름·번호와 같으면 **개인으로 보관하고 올리지 않는다**(`keepPersonal`과 같은 처리). 비교는 `PrivacyRules`의 정규화(공백·이모지·문장부호 무시)를 쓴다.
  3. 판단할 수 없는 녹음(파일 이름에 상대가 없고 연결도 안 됨)은 **보류**하고 연결을 다시 시도한다(통화 기록을 다시 읽는 주기에 맞춰). 보류가 24시간을 넘으면 올리지 않고 "정리하지 못한 통화"로 남긴다(v4.0의 "글자로 못 바꾼 통화"처럼 아침 보고의 건수에 들어가게 — 조용히 사라지면 안 된다). 업무 통화를 잃는 쪽보다 개인 통화가 올라가는 쪽이 더 나쁘다.
  4. `length` 연결 실패가 왜 늘었는지(긴 통화, 통화 대기·전환, 블루투스·차량 연결에서 녹음 길이와 통화 기록 길이가 벌어지는 경우 등 — 하트비트의 숫자와 코드로 추정) 보고, 안전하게 넓힐 수 있으면 허용 차이를 넓힌다(다른 통화와 잘못 연결될 위험이 커지면 넓히지 않는다).
  5. 이미 올라간 4건은 서버에서 "개인 내용"으로 처리됐다. 폰 쪽에서 그 번호들의 다음 통화가 같은 길을 타지 않는지 시험으로 확인한다.
- 하트비트(숫자만): `privacy{heldUnlinked, keptByName, releasedLinked, droppedUnlinked}` 같은 건수. 이름·번호·해시는 싣지 않는다.
- 시험: 연결 안 된 녹음 + 파일 이름이 개인 번호의 이름과 같음 → 올라가지 않고 개인 보관. 연결 안 됨 + 이름이 다름 → 올라감. 연결 안 됨 + 이름 없음 → 보류, 나중에 연결되면(개인이 아니면) 올라가고 개인이면 보관. 24시간 넘은 보류는 올라가지 않고 건수에 잡힘. 기존 연결된 경로는 그대로.

### r22-2 통화 카드가 막히는 원인 기록 (원인을 모르므로 이번에는 증거를 모은다)
- 붙이기에 실패한 순간의 원인 부호에 다음을 더한다(공개 API만, 숫자·부호만): 앱옵의 **원래 모드와 제한을 반영한 모드를 둘 다**(`unsafeCheckOpRawNoThrow`와 `unsafeCheckOpNoThrow` — 둘이 다르면 사용자 설정이 아니라 시스템 제한이다), 마지막 앱 업데이트 뒤 지난 시간 구간(`PackageInfo.lastUpdateTime`: 1시간 미만/6시간/24시간/48시간/그 이상), 설치한 쪽의 종류(`getInstallSourceInfo`의 설치 프로그램이 자기 자신인지/스토어인지/없음인지 — 패키지 이름은 싣지 않고 종류 부호만).
- 하트비트 `callCard.today`에 그날 첫 실패 시각(시:분)과 그 직전 마지막 성공 시각, 그리고 마지막 설치 시각을 숫자로.
- 통화 밖에서 권한 표시가 거짓으로 바뀌는 순간을 잡는다: 통화 시작·끝에서 권한 표시(`canDrawOverlays`, 두 모드)를 한 번씩 읽어 "통화 전 허용 → 통화 중 거부 → 통화 뒤 허용"인 통화 수를 센다.
- 막혔을 때 대신 뜨는 알림이 실제로 떴는지(`fallbackShown`)와 알림 권한·채널 중요도가 낮아져 있지 않은지(`fallbackMuted`)를 센다. 채널 중요도가 낮아져 있으면 하트비트로만 알린다(설정을 바꾸지 않는다).
- **고치기(해 볼 수 있는 것 하나):** 통화가 끝난 직후 권한이 다시 허용으로 돌아오는 것이 확인된 통화에 한해, 통화가 끝난 뒤에는 아무것도 띄우지 않는다(지금과 같음). 다른 우회(접근성 서비스, 전체 화면 알림, 다른 창 종류)는 **하지 않는다** — 시스템이 막는 것을 돌아가는 일은 사용자와 정한 뒤에 한다.
