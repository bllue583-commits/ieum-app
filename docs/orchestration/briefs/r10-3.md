# r10-3 지연 단축 (v2.9)

공통 지침 `docs/orchestration/worker-brief.md`를 먼저 읽고 따르세요. 브랜치 이름: `feature/r10-v29-r3`. 기준은 `feature/r10-v29`(v2.8 완성본).

설계: `docs/DESIGN_V3.md` 6.3절 **r10-3** 전부. 목표: 통화 종료 → 결과 반영 평균 25분.

## 담당 파일
- `pipeline/CallRecordWork.kt`: 업로드 직후 고유 작업 `ieum.calls.results`를 10분 뒤로 걸고, 기다리는 기록이 남아 있으면 10분 간격 체인(최대 12회, 그 뒤 1시간 틱으로 복귀). 결과 목록 조회는 `If-None-Match`(ETag, 설정에 마지막 ETag 저장; 304면 본문 없이 끝). 체인 횟수는 설정 키에.
- `docs/routines/hourly.md`: cron을 `*/30 7-22 * * *`(30분마다)로 바꾸는 지시(루틴 자체는 사용자가 교체; 문서에 "루틴 시간: 30분마다"를 적고 지시문 본문은 바꾸지 않음). `tools/inbox/watchdog.py`의 "루틴이 늦음" 기준이 있으면 30분에 맞춤.
- `ieum-inbox` 저장소 워크플로(`on: push, paths: inbox/**`로 루틴 깨우기)는 **이 묶음이 하지 않습니다**(워크플로 변경 금지). 대신 `docs/DEVELOPMENT.md`에 "push 때 루틴 깨우기" 제안을 한 단락으로 적어 두세요.
- 다른 묶음: r10-1이 `pipeline/call/*`·`AutomaticRecordingDiscovery`, r10-2가 `CallFollowupNotice.kt`와 `CallRecordWork`에 한 줄 호출(`CallFollowupNotice.onResult/sweep`). 그 줄과 충돌하지 않게 `CallRecordWork`의 결과 반영 함수 구조는 유지하세요.

## 시험
- 단위: 업로드 뒤 `ieum.calls.results`가 10분 뒤로 등록, 기다리는 기록이 있으면 다시 10분, 12회 뒤 등록 안 함(1시간 틱만), 결과가 다 오면 체인 중단. ETag 304 처리(가짜 HTTP). 하트비트에 `resultChain:{round,nextMs}` 추가(`PhoneStatus.Watch`에 필드 둘, `PhoneStatusTest` 키 목록 갱신).
