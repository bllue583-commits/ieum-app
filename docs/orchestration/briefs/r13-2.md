# r13-2 자막 정확도 1단계, 골든 측정 화면, 지시문 v7 (브랜치 `feature/r13-v33-r2`, 기준 `feature/r13-v33`)
공통 지침 `docs/orchestration/worker-brief.md`(기준 브랜치만 `feature/r13-v33`). 설계 기준은 **DESIGN_V4 3.2절**이다.
- 이번 범위: 1단계(1~3)와 2단계(4: 측정 도구와 화면).
- 3단계(5~9)는 상수를 바꾸지 않는다. 다만 골든 측정이 변형별로 돌 수 있게 **변형 스위치를 엔진 옵션으로만** 연다(기본값은 지금 그대로).
- 근거는 `docs/reviews/stt_v33_20261106.md`(협의안 전문)다.

- **소유 파일**
  - `AndroidWhisperEngine.kt`
  - `CallTranscriptionRunner.kt`(v3.2 r12-8이 바꾼 것 위에서, 대기열과 시간 한도 로직은 건드리지 않음)
  - `cpp/ieum_whisper.cpp`(+ 필요하면 `cpp/CMakeLists.txt`, 상수는 그대로)
  - `PipelineAudioMath.kt`(VAD 상수는 바꾸지 않음, 옵션만)
  - `PhoneStatus.kt`(`golden` 블록 + r13-1의 `guard` 블록 한 줄도 여기서 넣는다. 키 `PipelineSettingsKeys.GUARD_STATS`, 숫자 counts 필터)
  - 골든 도구(`tools/golden*`)
  - **새 골든 측정 Activity**(새 파일, 매니페스트 등록 포함)
  - `docs/routines/hourly.md`(v7), `RoutineDocTest`, `MessageWork.kt`
- **다른 묶음 파일:** 같은 시간에 r13-1이 `ClaudeCallAnalyzer.kt`·`CallRecordStore.kt`·`TasksScreen.kt`·`CallDigestWork.kt`·`ContactCards.kt`·카드 파일을 고친다. 건드리지 않는다.
- **`SettingsScreen.kt`:** r13-3 소유라 고치지 않는다. 진입 링크는 Activity 이름만 보고서에 적는다.
- **지시문 v7:** 지시문에서 `PROMPT_VERSION=7`을 쓰는 곳은 `ClaudeCallAnalyzer.kt`(r13-1)다. 바꿀 줄을 보고서에 적으면 통합 때 오케스트레이터가 넣는다. hourly.md와 RoutineDocTest는 7로 맞춘다.
- **키 커밋(이미 있음)**
  - `CallTranscript.Segment.uncertainNumbers`: 숫자 토큰 중 최소 확률이 0.5 미만인 것을 세그먼트 글에 나온 그대로 채운다. 3.2-1 토큰 확률에서 쓴다.
  - `PipelineSettingsKeys.GOLDEN`.
- **네이티브 빌드:** 로컬 툴체인은 `IEUM_SKIP_ANDROID_NATIVE=1`이라 cpp는 로컬에서 컴파일되지 않는다. GitHub ci나 release가 네이티브를 빌드하는지 워크플로를 보고 확인하고, cpp를 바꾼 뒤에는 그 빌드가 통과하는지 확인한다.
  - JNI 시그니처는 Kotlin 쪽과 함께 바꾼다.
  - JNI 결과 JSON이 바뀌면 옛 형식도 읽게 한다.
- **3.2-4 골든:**
  - Kotlin 점수가 `tools/golden_score.py`와 같은 값을 내는 시험을 넣는다.
  - 음성과 정답은 폰 밖으로 나가지 않는다. 하트비트에는 숫자만 올린다.
  - 합성 골든 turbo 측정(90분 기기 시험)은 하지 않는다. 방법만 보고서에 적는다.
- **완료 기준**
  - 3.2절 시험 목록 중 1~4 몫을 넣는다.
  - 로컬에서 컴파일하고 자기 시험 클래스를 돌린다.
  - check_ui_rules 0건, scan_export 0건.
  - push 뒤 GitHub ci가 성공해야 한다. 네이티브 빌드가 도는 워크플로가 있으면 그것도 성공해야 한다.
