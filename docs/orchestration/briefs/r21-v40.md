# r21: v4.0 「믿을 수 있는 두 접점」 — 조용히 잃는 곳을 막는다

브랜치 `feature/r21-v40`(작업 나무 `/home/claude/wt/r21`, 기준 = `feature/lean-calls`의 v3.9 빌드 1061). 보고는 한국어.

## 왜
원래 v4.0은 "오늘 통화는 오늘 정리"(엔진을 빠르게)였다. 11/15 폰 측정으로 접었다: q8_0 + 포그라운드가 아내 폰에서 녹음 1분에 1.9분(지금 엔진은 2.1~2.5분), 삼성이 오래 도는 작업을 4코어 등급(`moderate`, `abnormal`)으로 조인다 — CPU로는 실시간 이하가 안 된다(`docs/DESIGN_V8.md` 3절). 그래서 v4.0은 이 앱이 실제로 아내에게 닿는 두 곳(아침 05:30 카톡 보고, 전화가 올 때의 통화 카드)에서 **말없이 빠지는 것**을 막는 판이다. 근거는 `docs/eval/EVAL_1114.md` 3.2·3.4절과 `docs/DESIGN_V8.md` 6절. 먼저 그 두 문서와 `docs/HANDOFF.md` 0·4·5·6절을 읽을 것.

아내는 앱을 열지 않는다(열기 0회). 새 화면·새 설정은 만들지 않는다. 이 판에서 아내에게 달라지는 것은 ① 아침 카톡 첫머리에 "글자로 못 바꾼 통화 n건"이 생길 수 있다 ② 통화 카드가 더 자주 뜬다 — 이 둘뿐이어야 한다.

## 할 일

### r21-1 영구 실패한 통화를 보고에 (조용한 손실 1)
- 지금: 자막이 영구 실패한 통화(하트비트 `transcription.window14`: 14일 247건 중 실패 5, 영구 4, 원인 부호 `CodecException` 등)는 아침 보고의 "빠진 통화"에 들어가지 않는다. `CallRecordStore.kt`의 보고 범위 계산(`report.coverage`·state의 `pending`을 만드는 곳)이 FAILED를 `yesterdayCalls`에는 세고 `pending`에서는 뺀다 — 실제 코드를 읽어 정확히 어떻게 세는지 먼저 확인하고 보고에 적는다.
- 고칠 것: 어제 통화 중 **자막을 만들 수 없었던 통화 수**를 따로 세어(하트비트 `report.coverage.failed`, state와 보고서 머리의 같은 값) 카톡 리스트 보고의 머리말과 글 보고 첫 줄에 "글자로 못 바꾼 통화 n건"으로 적는다(0이면 아무것도 안 적는다). 문구는 50대가 봐도 바로 아는 말로, `tools/check_ui_rules.py` 통과. 통화 목록에서 그 통화는 지금 어떻게 보이는지 확인하고(이미 "정리할 수 없어요"류의 표시가 있으면 그대로) 보고에 적는다.
- 새벽 정리 지시문(`docs/routines/tidy.md`)과 `tools/report_check.py`가 이 값을 다루도록 맞춘다(지시문 본문을 바꾸면 버전을 11로 올리고 `RoutineDocTest`·`version_fields.py`·워치독의 버전 비교를 맞춘다). 채점(`tools/inbox/score.py` 항목 1)의 분모·분자 정의는 바꾸지 않는다.
- 새 빌드가 설치될 때마다 충전 중에 실패 녹음을 다시 시도하는 동작(W5, `requeueFailed`)이 **영구 실패**(`CodecException`, `ANDROID_STT_PCM_SIZE` 등 다시 해도 같은 것)까지 매번 다시 돌리는지 확인한다. 그렇다면 영구 실패는 빌드마다가 아니라 한 번만 다시 시도하게 한다(11/14: 하루에 빌드를 세 번 내자 측정대가 "자막 작업 중"으로 오래 밀렸다).

### r21-2 통화 카드 끝까지 (채점 항목 3: 14일 합 41.6%, 11/13 하루 39/42)
- 사실: 14일 194건 중 그려짐 39·`noPermission` 112. 하트비트의 권한 표시(`permissions.overlay`, `overlayMode` 0)는 줄곧 허용인데 전화가 오는 순간에만 실패한다. 11/13에 `addView:BadTokenException` 2건, 11/14 첫 통화 `noPermission`. 붙이기에 실패하면 `windowGone=true` 뒤 다시 시도하지 않고 알림으로 대신한다(`pipeline/call/CallCardOverlay.kt`, `CardStats.kt`).
- 고칠 것:
  1. 붙이기에 실패했거나(`addView` 예외) 붙였는데 그려지지 않았으면(`hidden`) **0.6초 뒤 한 번, 2초 뒤 한 번 더** 다시 붙인다(통화가 아직 울리거나 이어지는 동안만, 같은 창을 써서 카드가 두 번 뜨지 않게, 통화가 끝났으면 하지 않는다). 다시 붙여 그려지면 `drawn`으로 세고 `retried`도 센다.
  2. 실패한 순간마다 원인을 갈라 적는다(지금은 대부분 `noPermission` 하나): `canDrawOverlays` 값, 앱옵 원래 모드(`unsafeCheckOpNoThrow`), 예외 이름, 프로세스 나이(차가운 시작인지: 5초 미만/미만 아님), 화면 잠금, 화면 켜짐, 전화 상태(RINGING/OFFHOOK), 마지막으로 프로세스가 죽은 이유(`ApplicationExitInfo`의 reason 부호 — 사용자가 최근 앱에서 밀어 끈 것인지)와 그 뒤 지난 시간(분 단위 구간). 하트비트 `callCard.recent[]`(통화별 20건)와 `callCard.today.causes{부호: 건수}`에 **부호와 숫자만**.
  3. 워치독 규칙: 통화 카드 대체(`fallback`)가 하루 1건이라도 있으면 관리자 이슈(지금은 3건부터). `tools/inbox/watchdog.py`와 시험.
- 가설(확인 전, 코드로 뒷받침되면 그렇게 적고 아니면 버린다): 아내가 최근 앱 목록에서 앱을 밀어 끈 직후의 차가운 시작에서 창 붙이기가 잠시 막힌다. 기록이 이 가설을 가를 수 있게 한다.

### r21-3 "충전 중에만"을 지킨다 (채점 항목 6: 배터리 실행 11/12 59분, 11/14 40분 — 기준 25분)
- 사실: 아내 폰은 "충전 중에만"이 켜져 있다(`power.chargingOnly: true`). 그런데 하트비트 `power.prev.battery`가 11/14에 실행 5번·40분·녹음 0분, 11/12에 59분이다. 충전 중에 시작한 실행이 충전기에서 내려온 뒤에도 조각을 끝낼 때까지(2분 조각 하나에 4~5분) 이어 도는 것으로 보인다(`plugDropped`) — **먼저 코드(`CallTranscriptionRunner.kt`, `PowerPolicy.kt`, `PowerStats`)로 이 분이 어디서 생기는지 확인**한다(측정대의 실행이 여기에 섞여 세지는지도).
- 고칠 것: 충전 중 실행이 충전기에서 내려오면 **30초 안에 멈춘다**(엔진의 중단 콜백으로 조각을 멈추고, 끝난 조각은 남기고, 진행 중이던 조각은 다음 충전 때 다시 — 이어 하기 규칙 그대로). "충전 중에만"이 꺼져 있는 폰의 배터리 예산 실행(오늘 짧은 통화, 하루 20분/5%)은 그대로 둔다. 하트비트에 `power.today.unplugStops`(멈춘 횟수)와 버려진 작업 시간.
- 통과 기준(배포 뒤): "충전 중에만"이 켜진 날 `power.prev.battery.min` ≤ 3.
