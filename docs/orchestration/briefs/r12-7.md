# r12-7 녹음과 통화기록 짝짓기 (브랜치 `feature/r12-v32-r7`, 기준 `feature/lean-calls`)
공통 지침 `docs/orchestration/worker-brief.md`를 따르되 기준 브랜치는 `feature/lean-calls`다. 설계 기준은 **DESIGN_V4 2-2절**(실측 숫자와 가설 포함). 2.4-4(r12-4, 끝 시각 후보)와 v2.6 r7-4 대조 규칙도 읽는다.

1. 먼저 원인을 찾는다: `FirstPass.match`(와 그 호출부 `CallRecordWork`/`FirstPass` 처음 정리 경로, `reconcileCallLog`)가 녹음 하나의 시각으로 무엇을 쓰는지, call_records.started_ms가 언제 채워지는지(자동 발견, 이름 시각 보정, 처음 정리), 이미 이어진 통화기록을 후보에서 빼는 조건, 통화기록 쪽 시각(DATE=통화 시작)과 녹음 파일 이름 시각(삼성은 통화 시작 또는 끝)의 관계. RecordingGap.read(같은 저장소에서 창 안 파일을 찾음)와 무엇이 다른지 비교한다. 결론(근거 파일:줄)을 보고서 맨 위에.
2. 고친다: 대조 시각은 녹음 시각 `COALESCE(original_started_at_ms, filename_time_candidate_ms, modified_at_ms)`. 기존 규칙(창 1분 전~2분 후, 끝 시각 후보는 r12-4 조건, 길이 20%/15초, 후보 둘 이상이면 잇지 않음, 개인 번호)은 유지. 이미 저장된 못 이은 기록은 다음 패스에 다시 대조되게 한다(마이그레이션이 필요하면 MIGRATION_VERSION 올림, 직행 마이그레이션 시험 V24MigrationTest 회귀).
3. 진단: `callLogMatchStats.last.missGapMin`에 far 대신 부호 있는 분 차이를 10분 구간으로(-60..+60 밖은 far) 남긴다. 하트비트는 `counts` 필터 통과(숫자만).
4. 시험: 삼성 통화 녹음 파일 이름(예: "통화 녹음 김과장_241105_143022.m4a", "Call recording 010xxxx_20241105_143022.m4a" 등 RecordingNames 패턴 전부) 녹음 10개 + 통화기록 10건 → 10건 이어짐(처음 정리 경로와 새 녹음 경로 둘 다), 시작 시각 없는 기록도 파일 이름 시각으로 이어짐, 후보 둘이면 안 이음, 이미 이어진 통화기록 재사용 안 함.
5. 전체 `:core:test :app:testDebugUnitTest :app:lintDebug` 로컬 통과, check_ui_rules 0, scan_export 0. VERSION은 바꾸지 않는다(오케스트레이터가 정함).
