> 대상: 아내 폰(Galaxy S26)에 배포된 v3.9. 방법: ① 폰 하트비트 이력 199개(11/4~11/14, 실제 폰 것만)를 SQLite에 넣어 날짜별로 집계 ② 아내 폰의 업무 통화 표본 12건(21.7분)을 작업 환경에서 엔진별로 다시 돌림 ③ 공개 음성 실험([ASR_LAB_1113.md](ASR_LAB_1113.md)) ④ 독립 평가자(Opus 중간, 읽기 전용)의 코드·설계 평가 ⑤ 채점표 v3(`tools/inbox/score.py`). 통화 내용·이름·번호는 읽지 않았다(숫자와 부호만).
> 다음 계획은 [../DESIGN_V8.md](../DESIGN_V8.md).

## 0. 결론

1. **약속한 두 접점은 이제 돈다.** 아침 카톡 보고는 11/13 25/25건, 11/14 33/33건을 담았고(리스트 형식, 실패 0), 통화 카드는 11/13에 42건 중 39건(93%)이 실제로 그려졌다. 11/12까지는 카드가 거의 뜨지 않았다(11/10~11/12 0건).
2. **채점은 0/10이다.** 6개 항목은 관측 일수가 모자라서이고(10~14일 필요), 실제로 기준에 못 미치는 것은 넷이다: 적시성(11/13 지연 중앙값 565분, 기준 180분), 통화 카드 14일 합(41.6%, 기준 95%), 보안(서명 키가 우편함 토큰에서 나옴), 자막·약속 정답지 없음.
3. **아내는 앱을 열지 않는다.** 11/13·11/14 앱 열기 0회, 체크 완료 0회, [틀렸어요] 0회, 카톡에서 앱으로 넘어온 횟수 0회. 제품은 사실상 "카톡 보고 + 통화 카드"다. 화면 코드는 앱의 22%다.
4. **v4.0의 길이 좁혀졌다.** 빠른 엔진(SenseVoice) 초벌은 실제 통화에서 지금 엔진과 21.0% 달라 미리 정한 기준(15%)을 넘었다 → 두 번 돌리기는 접는다. 남은 길은 지금 엔진을 빠르게 하는 것 하나다(폰 측정 숫자 대기).
5. **가장 큰 위험은 보안이다.** 우편함 토큰이 APK 안에 있고 서명 키가 그 토큰에서 만들어진다. APK 하나가 새면 자막 읽기·쓰기와 가짜 업데이트가 함께 열린다.

## 3. 검증으로 새로 안 것

### 3.1 엔진 (v4.0의 근거)
- **빠른 엔진(SenseVoice)은 실제 통화에서 탈락.** 업무 통화 12건에서 지금 엔진과 글자 21.0% [18.3, 24.5] 다르고(통화별 15~32%, 기준 15% 이하), 지금 엔진의 숫자 107개 중 32개(30%)가 초벌에 없다. 공개 음성에서는 4.5~9.2%였다 — 낭독·합성 음성은 실제 통화보다 쉬웠다. 큰 모델(large-v3) 기준으로도 12건 전부에서 지금 엔진보다 멀다(22.3% 대 11.0%).
- **가벼운 판(q8_0)은 정확도가 지금(q5_0)과 같다**(공개 음성 5묶음에서 차이가 구간 안). 값은 속도뿐.
- **폰이 느린 이유.** 2분 조각 하나에 배경 실행 306초, 포그라운드 실행 249~257초(실시간의 2.1배). 포그라운드는 코어를 4개에서 6개로 풀어 주지만, 무선 충전에서는 발열 때문에 스레드를 4개로 묶어 둔 정책(`THREADS_OTHER`)이라 그대로 4개로 돈다. 아내는 무선 충전만 쓴다.
- **실험실은 폰을 대신할 수 있다.** 작업 환경에서 다시 만든 지금 엔진의 자막과 폰이 실제로 만든 자막의 차이는 숫자를 빼고 4.4%이고, 조각이 하나인 통화 5건 중 4건은 0.0%다.

### 3.2 통화 카드
- 14일 합 194건: 그려짐 39(11/13 하루), 권한 없음 112, 무시 11. **권한 없음이 11/10~11/12의 거의 전부였고, 11/13에 1건, 11/14 첫 통화도 권한 없음이다.** 하트비트의 권한 표시는 줄곧 "허용"이다 — 전화가 오는 순간에만 창을 붙일 수 없다는 뜻이고 원인은 아직 모른다. 11/13에는 `addView:BadTokenException`도 2건 있었다. 붙이기에 실패하면 다시 시도하지 않고 알림으로 대신하는데, 벨이 울릴 때 알림은 통화 화면 뒤에 묻힌다.
- 벨에서 카드까지 중앙값 60ms(따뜻한 시작), 1,537ms(차가운 시작, 기준 1,500ms를 살짝 넘음).

### 3.3 자막 정확도 (정답 없이 말할 수 있는 범위)
- 지금 엔진과 큰 모델은 실제 통화에서 글자 11.0% [9.2, 13.3] 다르다(낭독에서는 2~5%). 큰 모델도 정답이 아니다 — 공개 음성에서 큰 모델 하나는 지금 엔진보다 낫지 않았다.
- 숫자: 큰 모델의 숫자 107개 중 96개가 지금 엔진에 있다(90%). 다른 11곳은 사람이 들어야 누가 맞는지 안다(받아쓰기가 아니라 11곳 듣기).
- 이름·업체: 합성 음성에서 지금 엔진 75%(24/32). 초기 프롬프트 실험은 DESIGN_V8의 v4.3에 적는다 — 통화 상대의 이름만 주면 94%(30/32), 전체 이름 목록을 주면 실제 통화의 자막이 9.2% 흔들리고 숫자가 4개 덜 맞는다.
- 녹음 음량은 문제없다: 말소리 -18.8~-12.8 dBFS, 묵음 하한 아래로 떨어진 말소리 창 0%, 잘린 표본 0.012% 이하. 공개 음성에서 찾은 "조용한 말소리가 지워지는 문제"는 이 통화들에는 해당하지 않는다.

### 3.4 조용히 잃는 곳 (독립 평가자가 코드에서 확인)
- 자막이 영구 실패한 통화(14일 247건 중 실패 5, 영구 4 — `CodecException`)는 아침 보고의 "빠진 통화" 수에 들어가지 않고 워치독 규칙도 없다.
- 끝낸 일과 제목이 같은 새 요청은 14일 동안 만들어지지 않는다(매주 같은 정기 업무). 지금까지 막힌 것은 1건.
- 분석 결과가 세 번 적용에 실패하면 그 통화의 할 일은 사라지고 누계 숫자로만 남는다.
- 측정 표본을 지우는 주체가 폰 하나뿐이었다(폰을 잃으면 녹음이 우편함에 남는다). 11/14에 스위치를 꺼 지우게 했다.

### 3.5 측정대 자체의 버그 (11/14, 고침)
- 측정대의 글자 계산(`KoCer`)에 안드로이드가 못 읽는 정규식 문법 `(?U)`가 있어, 폰에서 처음 쓰는 순간 `ExceptionInInitializerError`가 났다. JVM 시험은 전부 통과했다. 이 오류는 Exception이 아니어서 기록 없이 실행을 끝냈고, 측정은 밤새 "실행 중"만 다시 찍었다. 빌드 1059(오류를 잡고 멈춘 곳을 하트비트에)로 위치를 찾고 1061에서 고쳤다. 에뮬레이터 기기 시험(`t0_benchTextMathOnThisAndroid`)과 "JVM만 받는 정규식 문법" 검사를 더했다.
- 교훈: 폰에서만 도는 코드는 에뮬레이터에서 한 번은 돌려야 한다. 아내 폰을 시험대로 쓰면 한 번 확인에 한 시간이 든다.

## 5. 이 평가의 한계
- 관측이 짧다: v3.7 이후 3일, v3.9 이후 하루. 사용 숫자는 이틀치다.
