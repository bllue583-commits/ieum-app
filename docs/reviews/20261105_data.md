## 0. 요약 (심각한 것부터)

1. **보호 DB는 "통째 암호화 파일" 하나이고, 열 때마다 전체를 복호화해 메모리 SQLite에 다시 넣습니다. 쓸 때마다 전체를 JSON으로 만들어 암호화하고 fsync합니다.** `CallRecordStore`를 `use{}`로 열고 닫을 때마다 참조가 0이 되면 상태를 버리므로(`ProtectedDatabase.java:88-91`), 홈 화면 하나가 DB를 7번 통째로 복원합니다(`HomeActivity.kt:87-110`). 트랜잭션 밖의 `port.execute`는 문장 하나마다 DB 전체를 다시 씁니다(`AndroidSqlPort.java` execute → `transaction`). 그래서 **오버레이(100ms 안 조회)는 지금 구조로는 불가능합니다.** 프로세스가 죽어 있으면 첫 조회 때 복호화와 복원 비용(DB 크기에 비례, 수백 ms에서 수 초로 추정)을 모두 냅니다. 사전 계산한 작은 "상대 카드" 저장소가 필요합니다(6절).
2. **복구 파일(.new/.bak)이 하나라도 남으면 DB가 영구히 잠깁니다.** `readMainPreservingArtifacts`가 `held=true`로 막고 자동 복구가 없습니다(`ProtectedDatabase.java:140-145`). 이렇게 되면 앱 전체(통화·체크할 일·장부)가 멈춥니다. 여기에 더해 **"저장 공간 n%"와 80% 경고는 실제로는 동작하지 않습니다.** 둘 다 `getDatabasePath(callbrief-local-v2.db)`를 재는데(`CallDigestWork.kt:180`, `CallSettingsActivity.kt:137`), 실제 파일은 `noBackupFilesDir/protected-databases-v1/…sealed`라서 값이 늘 null입니다. 16MB 한도를 넘거나 전체 행 10만 개를 넘으면(`ProtectedDatabase.java:193-206`, 행 수는 모든 표를 합친 값) 모든 쓰기가 실패하는데, 아무 경고 없이 그렇게 됩니다.
3. **callLog.since.recorded=0의 원인:** 통계 열은 정상적으로 채워집니다(`CallRecordStore.kt:940-946`의 `recorded`는 `call_record_log`에 이어진 수신·발신 통화 수). 따라서 **대조 자체가 0건 성공**한 것입니다. 파일 이름에 사람 이름만 있는 삼성 녹음은 통화기록의 `CACHED_NAME`이 공백을 뺀 글자까지 똑같아야만 잇고, 이름이 다를 때 시각과 길이만으로 잇는 길은 없습니다(`FirstPass.kt:92-97`). 또 시각 창은 "통화기록 시각이 녹음 시각의 2분 전부터 1분 뒤 사이"입니다(`FirstPass.kt:86-87`). 녹음 시각이 비어 있거나(`started_ms IS NOT NULL` 조건, `CallRecordStore.kt:880`), 파일 이름의 시각이 통화가 끝난 시각이면 3분이 넘는 통화는 모두 빠집니다[추정]. 실패 이유를 세는 진단 카운터가 없어 원인을 하나로 확정하지 못했습니다. 7절에 진단 방법을 적었습니다.
4. **같은 번호를 쓰는 같은 사람이 두 사람으로 갈라집니다.** `NameKey.canon`은 "김과장"(성+직책)을 그대로 키로 둡니다(`NameKey.kt:24`). 같은 번호로 다음에 "김민수"가 들리면 비슷하지도 않고 이름이 빈 사람도 아니어서 같은 번호의 새 사람이 생깁니다(`CallRecordStore.kt:344-358`). 호칭 목록에는 건설 현장에 흔한 "기사", "씨", "감리"가 없어(`NameKey.kt:7`) "박기사님"과 "박기사"만 하나로 묶이고, "김민수 씨"는 "김민수씨"라는 다른 키가 됩니다. 장부가 사람마다 이렇게 둘로 나뉘면 오버레이에도 같은 상대 카드가 두 장 뜹니다.
5. **장부 흐름은 코드상 이어져 있지만 지시문이 모호합니다.** hourly.md 4번은 "사람: 더하거나 … 고친다" 한 줄뿐이고, `counterpartId`로 `people[]` 항목을 만드는 규칙(id·name·company 값)이 적혀 있지 않습니다(`hourly.md:35`). 폰 `applyLedger`는 장부에 있는 id만 반영합니다(`CallRecordStore.kt:752`). 화면의 사람·업체는 결과의 counterpart로 폰이 직접 만들기 때문에(`applyAnalysis` → `upsertPerson`, `CallRecordStore.kt:536-546`), 장부가 비어 있어도 폰 화면은 채워질 수 있습니다. 하지만 새벽 정리와 별칭, 잠금은 저장소 장부를 기준으로 하므로 지시문에 명시적인 문장이 필요합니다(5절).

추가로 짧게 적을 것:
- 코디네이터 정정에 따라 "옛 형식 요청"은 폰 빌드가 옛 것이었던 탓으로 봅니다. **현재 코드의 요청 경로는 정상입니다.** 새 기록은 `CallInbox.job`(format 3, recordKey, atMs, counterpartId, promptVersion 5, system 없음, `CallInbox.kt:118-121`, `CARRY_RULES=false` `:113`)으로, 처음 정리 기록은 `CallInbox.batch`로 올라갑니다(`CallRecordWork.kt:110-127`). 이 경로를 막는 플래그나 조건은 없습니다. 동의(`CONSENT_GRANTED`)와 개인 번호만 전송을 막습니다(`CallRecordWork.kt:97-106`).
- 폰 장부 버그: 사람 합치기(`mergedInto`)는 `person_aliases`를 새 사람으로 옮기지 않아 별칭이 고아가 됩니다(`CallRecordStore.kt:779-782`). 새벽 제안을 적용할 때 rev를 비교하지 않아, 상태를 올린 뒤 들어온 통화의 갱신을 옛 판단으로 덮어쓸 수 있습니다(`applyTidy`, `:825-868`).

## 2. DB 스키마 (앱이 쓰는 표 전부)

## 6. 오버레이용 조회 설계 (모모콜 방식, v3.0)

### 6.1 지금 가능한가: 질의는 가능하지만 시간이 안 됨

필요한 데이터는 모두 있습니다.
- 번호 → `people_phones`(PK 첫 열 phone_key, 인덱스 있음) → `people` → `companies`
- 최근 요약 3건: `call_links`(person_id) JOIN `call_records`
- 열린 체크할 일: `call_task_bindings`+`call_links` 또는 `task_companies`
- 진행 중인 일: `issues.companies` JSON의 업체 이름
- 마지막 통화: `call_log.start_ms`(number_key)

메모리 SQLite에서 위 질의는 행 수천 개 기준 수 ms 수준입니다[추정]. call_links.person_id, task_companies.company_id, call_log.number_key에 인덱스가 없어 전체를 훑지만, 메모리 안이라 10ms 안쪽으로 봅니다[추정].

**걸리는 곳은 여는 비용입니다.** 전화가 오는 순간 이음 프로세스는 보통 꺼져 있거나 DB 참조가 0입니다. 그때 `ProtectedDatabase.open`이 하는 일은 다음과 같습니다(`:107-131`).
1. Keystore 키 조회와 증명 복호화
2. 파일 전체 읽기(최대 16MB)
3. AES-GCM 복호화
4. `new String`과 `JSONObject` 파싱
5. 모든 표의 행 INSERT와 인덱스 재생성
6. foreign_key_check

DB 2~5MB 기준 0.5~3초로 추정합니다(측정 안 함). 게다가 `CallRecordStore` 생성자는 열 때마다 스키마 확인과 ALTER 확인, `local_files` 보정 UPDATE를 트랜잭션으로 돌립니다(`CallRecordStore.kt:150-171`). 내용이 바뀌지 않으면 persist는 생략되지만 snapshot(전체 JSON 생성)은 매번 합니다(`ProtectedDatabase.java:156`). **100ms 목표는 지금 구조로 불가능합니다.**

### 6.3 번호 정규화 (지금은 셋이 서로 다름, 문제 14)

| 입력 | `MessageIntake.phoneKey` | `counterpartKey` | `PrivacyRules.normalizePhone` |
|---|---|---|---|
| `+82 10-1234-5678` | 01012345678 | 821012345678 | 01012345678 |
| `+82 (0)10-1234-5678` | **001012345678** | 8201012345678 | 01012345678 |
| `010-1234-5678` | 01012345678 | 01012345678 | 01012345678 |
| `+82 2-123-4567` | **null** | 8221234567 | 021234567 |
| `02-123-4567` | 021234567 | 021234567 | 021234567 |
| `1588-1234` | null | 15881234 | 15881234 |

(phoneKey 값은 실제 계산으로 확인했습니다.) 통화기록과 문자는 `phoneKey`, 녹음 파일은 `counterpartKey`를 씁니다. 오버레이가 받는 번호는 E.164(`+82…`) 형태입니다.

제안 `core/PhoneKey.of(raw): String?`:
1. NFKC 정규화 후 숫자와 앞의 `+`만 남김
2. `+82`나 `0082`로 시작하면 떼고, 다음이 `0`이 아니면 `0`을 붙임. `(0)`은 제거
3. `82`로 시작하고 길이가 11~12면 위와 같이 처리
4. `PrivacyRules.validKoreanPhone`을 통과하면 반환. 15xx/16xx/18xx 대표번호는 별도 키로 허용(오버레이에 업체 대표번호가 필요할 수 있음)
5. 그 밖은 null

`counterpartKey`, `MessageIntake.phoneKey`, `FirstPass.readCallLog`, `CallLogReport`가 모두 이것을 쓰게 하고, `MIGRATION_VERSION`을 올려 `people_phones`, `people.phone_key`, `call_records.counterpart_key`, `call_log.number_key`, `personal_numbers`를 다시 계산합니다(키가 충돌하면 합침).

### 6.4 예상 시간 [추정]

| 경로 | 시간 |
|---|---|
| 캐시 적중 | <1ms |
| 프로세스는 살아 있고 캐시 없음 → 카드 파일 읽기 | 20~60ms |

콜드 스타트는 Android 프로세스 시작 비용이 대부분입니다. 오버레이는 먼저 "번호, 이름"을 띄우고 카드를 이어서 채우는 2단계로 그리면, 사용자가 느끼는 시간을 100ms 안팎으로 맞출 수 있다고 봅니다. 큰 DB를 직접 열면 0.5~3초가 걸립니다.

## 7. callLog.since.recorded = 0의 원인 분석

**통계 열은 정상입니다.** `PhoneStatus.window`는 `stored.recorded`(= `callLogTally`의 `rec`)를 그대로 씁니다(`PhoneStatus.kt:74-83`). `rec`은 `type IN (1,2) AND log_id IN call_record_log`입니다(`CallRecordStore.kt:942`). `unrecorded=678`은 `call_log`에 통화기록이 저장되어 있다는 뜻이므로 `reconcileCallLog`는 실행되어 커밋되었습니다. 같은 트랜잭션 안의 `FirstPass.match`가 0쌍을 돌려준 것입니다.

0쌍이 나올 수 있는 코드상 경로(가능성 높은 순서, 모두 추정):

1. **이름만 있는 파일 이름과 CACHED_NAME 불일치**
   - 삼성 녹음은 연락처 이름으로 파일을 만듭니다. `counterpart()`가 이름을 꺼내면 `counterpartKey`는 그 이름 그대로입니다(`CallTranscriptionRunner.kt:185-196`, `CallRecordStore.kt:127`).
   - 이때 `named = e.name!=null && noSpace(e.name)==noSpace(r.counterpart)`가 참이어야 합니다(`FirstPass.kt:94`).
   - CACHED_NAME이 null이거나(삼성 통화기록에서 자주 비어 있음), 연락처 표기가 파일 이름과 한 글자라도 다르면(이모지, 괄호, 파일 이름에서 바뀐 문자, `_`가 들어간 이름은 `split('_')`에서 잘림) 후보에서 빠집니다.
   - **이름을 모르면 시각과 길이로 잇는 대체 경로가 없습니다**(`key==null`일 때만 후보 하나 규칙, `:95,103`). 실사용자의 업무 상대는 거의 연락처에 있으므로 대부분의 녹음이 이 경로입니다.
2. **파일 이름 시각의 의미**: 창은 "통화기록 시각 ∈ [녹음 시각−120초, 녹음 시각+60초]"입니다. 녹음기가 파일 이름에 **통화가 끝난 시각**을 넣는 기종이면 2분이 넘는 통화는 모두 창 밖입니다. 기종 확인이 필요합니다.
3. **started_ms가 비어 있음**: `open` 목록이 `started_ms IS NOT NULL`인 것만 고릅니다(`CallRecordStore.kt:880`). 파일 이름 시각 보정은 `local_files` 행이 있을 때만 됩니다(`:165-170`). 옛 경로로 들어온 기록이면 계속 비어 있습니다.
4. 기록 자체가 적음: 678건은 녹음된 것과 안 된 것을 합친 모든 통화이고, 이음 기록은 자막이 끝난 것(약 30건)뿐입니다. 0이 되려면 그 30여 건이 모두 1~3번에 걸려야 합니다. 1번이면 충분히 설명됩니다.

확인 방법(내용 없이):
- (a) `status/calllog.txt`의 "녹음" 열과 같은 시각대의 앱 기록(`shortId`)을 사람이 비교합니다. 이미 우편함에 있습니다(`CallLogReport.kt:72`).
- (b) `reconcileCallLog`에 실패 이유 카운터를 넣어 하트비트에 올립니다: 시각 없음, 창 안 후보 0, 길이 불일치, 이름 불일치, 후보 2개 이상, 성공. 이름 불일치는 "CACHED_NAME null"과 "다름"으로 나눕니다. 추가로 이어진 쌍의 시각 차(초) 분포를 둡니다(E8 히스토그램).

고칠 것:
- 이름이 다르면 시각과 길이 후보가 정확히 하나일 때 잇습니다(`key==null`과 같은 규칙).
- 이름 비교는 `NameKey.canon` 양쪽 비교 + 한쪽이 다른 쪽을 포함하면 일치로 봅니다.
- 창은 (b)의 실측으로 정합니다.

이 대조가 실패하면 다음이 함께 일어납니다.
- 이름 기록이 번호 키를 얻지 못합니다(`:889`). 그래서 같은 사람의 문자(번호 키)와 통화(이름 키)가 다른 사람으로 갈라집니다.
- `[통화기록]`과 `[통화 방향]`이 요청에서 빠집니다(`:471-474`). 화자 판정의 1순위 근거와 날짜 기준이 사라집니다.
- 개인 번호와 맞춰진 녹음을 지우는 장치(`forgetCall`)도 동작하지 않습니다.

**정확도 저하의 근본 원인 중 하나이므로 v3.0 전에 우선 고쳐야 합니다.**

## 8. 장부 적용(applyLedger, applyTidy, applyAnalysis) 순서와 경계

- **트랜잭션 경계** [코드]: 세 함수는 각각 `port.transaction` 하나입니다(`:514,741,825`). 실패하면 전체가 롤백되고(`ProtectedDatabase.java:149-162`), 바깥 트랜잭션에서만 persist합니다. 부분 실패는 없습니다.
- **SecureSettings와의 경계**: 장부 rev(`LEDGER_REV`), 새벽 rev(`TIDY_REV`)는 DB 밖의 설정에 저장됩니다(`CallRecordWork.kt:195,202`). DB 반영과 rev 저장 사이에 종료되면 다음 실행에서 다시 반영합니다. `applyLedger`와 `applyTidy` 모두 다시 실행해도 안전합니다. `applyTidy`의 create는 `isDuplicate`가 같은 제목을 막습니다. 반대로 rev 저장이 `runCatching`으로 실패하면(`:20`) 매시간 다시 반영합니다. 문제는 아닙니다.
- **순서**: 한 실행 안에서는 ① 사용자 수정 올리기 → ② 장부 받기 → ③ 결과 적용(통화 시각순) → ④ 새벽 제안 → ⑤ 보내기 순입니다(`CallRecordWork.kt:57-95`).
  - ③의 `upsertPerson`이 결과 counterpart로 업체와 직책을 덮을 수 있고(`COALESCE(?,company_id)`, `:362`), ②에서 장부가 고친 값이 다음 장부 rev까지 뒤집힙니다. 매시간 rev가 오르므로 다음 실행에서 장부가 다시 이깁니다. 낮음.
  - `rev` 비교는 "같으면 건너뜀"이라, 장부를 다시 만들어 rev가 낮아져도 반영합니다(`:193`). 의도대로입니다.
- **사용자 수정 보존**:
  - 이름 잠금(`name_locked`)은 장부가 같은 이름을 실어 오면 풀립니다(`:755-757`). 맞습니다.
  - 체크할 일은 `workflow_item_history`가 있거나 revision이 다르면 AI가 제목과 기한을 바꾸지 않고 ai_note만 붙입니다(`:580-584`). `applyTidy`도 같은 조건입니다(`:827-829`). 맞습니다.
  - `undoDone`은 history를 남기지 않지만, `completeItem`의 history가 남아 이후에도 사용자 소유로 유지됩니다. 맞습니다.
- **데이터가 꼬일 수 있는 순서**:
  - 문제 12: 새벽 state를 올린 뒤 들어온 결과를 제안이 덮습니다.
  - 문제 13: 합친 사람의 별칭이 고아가 됩니다.
  - 결과 파일을 적용한 뒤 삭제 전에 종료되면 다시 읽지만, `state==ANALYZED`면 건너뜁니다(`:516`). 안전합니다.

## 9. 메인 스레드 접근

- 화면은 모두 `withContext(Dispatchers.IO)`로 엽니다(HomeActivity:71, CompaniesActivity:47, TodayCallsActivity:60·165, CallTasksActivity:33·122, TaskActions, CallSettingsActivity:131).
- `GeneralLocalStore`는 메인 루퍼를 검사하지만(`GeneralLocalStore.kt:51`), **`CallRecordStore`에는 검사가 없습니다.** 오버레이 코드가 실수로 메인 스레드에서 열면 수 초 동안 멈춥니다(ANR 위험). 같은 검사를 넣기를 권합니다.
- `ProtectedDatabase.State.transaction`은 `synchronized`입니다. 매시간 분석이 긴 트랜잭션(전체 snapshot과 persist)을 도는 동안 화면의 `read`도 같은 객체의 모니터를 기다립니다(`ProtectedDatabase.java:78-81,146-147`). 화면이 수백 ms씩 멈출 수 있습니다[추정].
