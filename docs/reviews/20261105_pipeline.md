## 5. 자동화·지연 단축 구조 제안 5개

1. **우편함 push → 루틴 즉시 호출.** `ieum-inbox`에 `on: push, paths: inbox/**` 워크플로를 두고, 5~10분 디바운스 뒤 루틴 실행 API를 부릅니다. 지금 코드와 워크플로에는 push형 호출이 없습니다(cron만, `inbox-e2e.yml:11`도 cron).
   - 효과: 루틴 대기가 평균 30분에서 5~10분으로 줄고, 빈 실행이 사라져 주간 한도도 아낍니다.
   - 위험: 루틴을 깨우는 공개 HTTP API가 있는지, 그 인증 비밀을 Actions에 둘 수 있는지 미확인. cron은 보험으로 하루 3회 남겨야 합니다. **[추정]**
2. **폰 결과 수신을 "업로드 + N분"으로.** 업로드 직후 15분과 25분, 그 뒤 매시 루틴 + 10분에 `CallResultsWork`를 걸고, ETag라 비용은 없습니다(`CallRecordWork.kt:261-283`).
   - 효과: 수신 지연이 45분에서 5~10분으로 줄어듭니다.
   - 위험: GitHub 요청이 늘지만 304는 한도에 거의 안 걸립니다.
3. **처음 정리와 평소 흐름의 완전 분리.** 처음 정리 시작 시각 기준을 버리고 "최근 7일 = 평소(단건, 충전 조건 없음), 그 이전 = 처음 정리"로 나눕니다. b- 관문은 10/1 이전 행을 무시하고, 6시간 기다린 기록은 덜 찬 묶음으로도 보냅니다.
   - 효과: 업데이트 시점과 상관없이 오늘 통화가 오늘 보고에 들어갑니다(표 #1, #2 해소).
   - 위험: 장부의 시간순이 일부 뒤섞입니다. 장부는 "보태기만" 규칙이라 영향은 작습니다.
4. **발견 경량화: MediaStore 질의와 통화기록 트리거 140초.** SAF 트리 전체 목록 대신 통화 종료 시 최근 1시간 수정 파일만 질의합니다. 최소한 SAF 목록에서 10/1 이전을 먼저 버리고 한도는 남긴 것에만 적용합니다. 트리거 지연을 140초로 하면 partial 규칙을 한 번에 통과합니다.
   - 효과: 통화 종료에서 대기열까지 약 2.5분, 폴더 크기와 무관.
   - 위험: MediaStore는 READ_MEDIA_AUDIO 권한을 하나 더 요구합니다. SAF 방식만 고치면 권한은 그대로입니다.
5. **백그라운드 자동 설치와 "미설치" 감시.** 다운로드와 검증이 끝나면 바로 `PackageInstaller` 세션을 commit합니다. Android 12 이상, 설치자 조건이 맞으면 무인 설치되고, 아니면 확인 알림이 남습니다. 하트비트에 `updateReadySinceMs`를 넣고 워치독은 24시간 규칙을 둡니다.
   - 효과: 고친 버전이 하루 안에 들어갑니다. 이번 사고의 근본(옛 빌드로 계속 돔)을 막습니다.
   - 위험: 직접 설치한 APK는 설치자가 파일 관리자라 무인 설치가 거부될 수 있습니다. 첫 무인 업데이트 뒤에는 이 앱이 설치자가 되므로 다음부터는 가능할 것으로 봅니다. **[추정, 실기기 확인 필요]**

덧붙여 1~2분 목표의 병목 순서: ① 루틴 cron(최대 60분) ② 결과 수신 :45(최대 60분) ③ 자막 계산(통화 길이 × 1.2~1.4) ④ 발견 4분. ③은 통화 길이에 비례해 줄일 수 없습니다. 5분 통화라면 이론 최단은 통화 종료 뒤 약 10분입니다(발견 2.5분 + 자막 6~7분 + 루틴 즉시 1~2분). "1~2분"은 지금 구조(폰 Whisper + 구독 루틴)로는 불가능하고, 10~15분이 현실적인 목표입니다.
